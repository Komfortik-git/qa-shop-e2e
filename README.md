# QA Shop: Playwright и мониторинг

Учебный магазин «Лавка» из предоставленного qa-shop.zip, браузерные e2e-тесты и воспроизводимый стенд Prometheus/Grafana. Исходные server.js, products.json и public/ не изменены. Оригинальная документация: [APP_README.md](APP_README.md).

## Ссылки

- Магазин: https://ccd-bracelet-baghdad-bedrooms.trycloudflare.com
- Grafana: https://orbit-build-opportunity-alexandria.trycloudflare.com/d/qa-shop

Адреса получены 23.11.2026; актуальны пока работают эти процессы туннелей. Grafana открывается без пароля с ролью Viewer. Prometheus доступен только локально.

## Запуск тестов

Требования: Node.js 22+, npm. Docker для e2e не нужен.

```bash
npm ci
npx playwright install chromium firefox webkit
npm test
npm run test:report
```

На Linux/CI: `npx playwright install --with-deps chromium firefox webkit`.

Playwright автоматически запускает пять отдельных экземпляров приложения на портах 3107–3111, каждый с новым временным каталогом данных. У каждого браузерного профиля собственная база. Занятый порт вызывает ошибку вместо подключения к чужому процессу. `/api/test/reset` отключён. Один worker исключает случайное влияние соседних тестов; каждый тест получает новый browser context, аккаунты используют уникальные адреса @example.test. Фиксированные ожидания sleep и retries не используются.

```bash
npm run test:desktop  # полный набор: Chromium + Firefox + WebKit
npm run test:mobile   # Android Chrome (Pixel 7) + iPhone WebKit (iPhone 13)
npm test -- --project=chromium  # быстрый прогон одного браузера
```

Мобильные профили эмулируют экран, touch, user-agent и параметры устройства. Это не испытание на физических Android/iPhone и не запуск установленного Safari.

Тест последней единицы дополнительно создаёт отдельный процесс и JSON-базу с остатком 1. Два покупателя проходят UI до подтверждения; два настоящих POST /api/orders выпускаются через общий барьер. Ответы сервера не подменяются. Проверяется ровно один HTTP 201, один 409, один сохранённый заказ, остаток 0, очистка корзины победителя и сохранение корзины второго покупателя.

Проверка уже запущенного стенда:

```powershell
$env:BASE_URL = 'https://YOUR-SHOP-URL'
npm test -- --project=chromium
Remove-Item Env:BASE_URL
```

Bash: `BASE_URL=https://YOUR-SHOP-URL npm test -- --project=chromium`.

Внешний прогон одного desktop-профиля создаёт тестовые аккаунты и пять заказов, уменьшает остаток шоколада на 4 и сертификата на 1. Он не сбрасывает данные. Тест последней единицы при BASE_URL явно пропускается, поскольку требует собственной контролируемой базы. После многократных запусков остатки могут закончиться — для воспроизводимых полных прогонов используйте автоматически создаваемый локальный экземпляр. Не запускайте несколько полных прогонов одновременно против одной базы.

Расширенный набор: **54 сценария, 153 выполнения в пяти профилях**. Последний локальный прогон: **133 проверки прошли без ошибок, 20 ожидаемо воспроизвели известные дефекты; неожиданных падений и пропусков нет**. Результат последнего прогона и разбивка по браузерам: [evidence/expanded-validation.json](evidence/expanded-validation.json).

- Chromium, Firefox, WebKit: по 45 сценариев, включая границы доставки и конкурентную покупку.
- Mobile Chromium (Pixel 7, 412×839) и Mobile WebKit (iPhone 13, 390×664): по 9 сценариев.

- Playwright учитывает ожидаемые ошибки как успешный результат suite; это не означает отсутствие багов.

Тесты дефектов находятся в `tests/known-bugs.spec.js`, `tests/quantity-validation.spec.js` и `tests/mobile.spec.js`; их названия содержат BUG-ID. `test.fail()` выставляется только перед проверкой известного нарушения, после успешной подготовки сценария. Неожиданное исправление приводит к unexpected pass и требует пересмотра пометки. Чтобы увидеть известные дефекты как обычные красные падения:

```powershell
$env:STRICT_BUGS = '1'
npm run test:bugs
Remove-Item Env:STRICT_BUGS
```

Bash: `STRICT_BUGS=1 npm run test:bugs`.

Сохранить компактную сводку последнего прогона: `node tools/summarize-results.js`.

HTML-отчёт: `playwright-report/index.html`; JSON: `test-results/results.json`; screenshot, video и trace сохраняются для ошибок. GitHub Actions запускает все пять профилей и сохраняет оба каталога как артефакты на 14 дней.

## Найденные баги

Все ниже воспроизведены на исходном приложении, без исправлений его кода.

### BUG-01 — адрес виден при самовывозе (Medium)

1. Добавить товар и перейти к оформлению.
2. Выбрать «Самовывоз».
3. Посмотреть поле «Адрес доставки».

Ожидается: адрес скрыт, доставка бесплатна. Фактически доставка бесплатна, но адрес виден. JS выставляет `hidden`, а CSS `.form label { display: grid; }` переопределяет браузерное скрытие. Воспроизведение: `known-bugs.spec.js`, BUG-01.

### BUG-02 — количество 0 добавляет одну единицу (Medium)

1. Открыть карточку доступного товара.
2. Ввести количество 0.
3. Нажать «Добавить в корзину».

Ожидается: ошибка валидации, корзина не изменяется. Фактически HTTP 201, добавляется 1 шт. В API выражение `qty || 1` заменяет 0 на 1 до проверки. `min=1` у поля само по себе не блокирует кнопку вне submit-валидации. Воспроизведение: BUG-02. Дополнительная проверка в quantity-validation.spec.js: очистить поле количества полностью — пустая строка тоже превращается в 0, а затем в 1. Дефект воспроизводится в обоих вариантах.

### BUG-03 — аккаунт B видит заказ аккаунта A в том же браузере (High)

1. Зарегистрировать A, оформить заказ, запомнить его URL.
2. Выйти и зарегистрировать B в той же браузерной сессии.
3. Открыть сохранённый URL заказа A.

Ожидается: «Заказ не найден», персональные данные A недоступны B. Фактически показываются состав заказа, имя и телефон A. Доступ разрешается по прежнему sid даже при входе другого пользователя. Воспроизведение: BUG-03; тест дополнительно проверяет, что текущий пользователь действительно B.

### BUG-04 — принимается телефон из одной цифры (Medium)

1. Добавить товар, выбрать самовывоз.
2. Заполнить имя, в телефон ввести `1---------`.
3. Подтвердить заказ.

Ожидается: HTTP 400 и ошибка поля телефона. Фактически HTTP 201, заказ создан с недействительным телефоном. Регулярное выражение считает дефисы и пробелы частью требуемой длины вместо проверки числа цифр. Воспроизведение: BUG-04.

### BUG-05 — пустое количество в корзине удаляет товар (Medium)

1. Добавить 2 шт. товара и открыть корзину.
2. Очистить поле количества, не вводя новое значение.
3. Перейти фокусом на другое поле (Tab).

Ожидается: ошибка пустого значения либо возврат предыдущего количества; позиция сохранена. Фактически отправляется PATCH с qty=0, HTTP 200, товар удаляется без подтверждения. Фронтенд преобразует пустую строку через Number('') в 0, а сервер трактует 0 как удаление. Явное нажатие «−» при количестве 1 проверено отдельно и корректно удаляет позицию. Воспроизведение: quantity-validation.spec.js, BUG-05.

### BUG-06 — на мобильном экране недоступна история заказов (Medium)

1. Открыть магазин на экране шириной 412 или 390 CSS px.
2. Зарегистрироваться либо войти.
3. Попытаться перейти к «Мои заказы» через интерфейс.

Ожидается: доступная ссылка или мобильное меню с историей. Фактически ссылка скрыта, альтернативного меню нет. CSS при ширине ≤720 px скрывает весь .nav через display:none, хотя JS снимает hidden с #nav-orders. Прямой URL #/orders существует, но пользователь не может открыть его через навигацию. Подтверждено в эмуляции Android Chrome и iPhone WebKit. Воспроизведение: mobile.spec.js, BUG-06.

## Docker, Prometheus и Grafana

Скопировать `.env.example` в `.env`, задать случайный длинный `GRAFANA_ADMIN_PASSWORD`.

```bash
docker compose -f compose.observability.yaml up -d --build
docker compose -f compose.observability.yaml ps
```

- Магазин: http://localhost:13000
- Grafana: http://localhost:13001/d/qa-shop
- Prometheus: http://localhost:19090
- Метрики: http://localhost:13000/metrics

Образы мониторинга и туннелей зафиксированы digest. Отдельный `Dockerfile.assignment` использует npm ci, запускает приложение от node и копирует только runtime-файлы. Исходный Dockerfile сохранён. Данные магазина, Grafana и Prometheus находятся в отдельных Docker volumes. Prometheus хранит 7 дней, максимум 512 MB. Ограничена память контейнеров.

Источник данных и дашборд из 20 панелей создаются автоматически через provisioning; ручная настройка в UI не требуется. Интервал scrape/refresh — 15 секунд.

Панели: доступность /metrics; uptime Node.js; RPS без /metrics; доля 5xx; 4xx и p95 API по маршрутам; число и сумма заказов за период; доставка/оплата; средний чек; добавленные единицы товаров; регистрации и ошибки входа; сессии; товары без остатка; память RSS; CPU; p99 event loop; абсолютные счётчики заказов и суммы с запуска.

Особенности интерпретации:
- `shop_revenue_rub_total` — сумма оформленных заказов с доставкой, **не подтверждённая оплата**.
- `shop_active_sessions` — записи в памяти, **не число онлайн-пользователей**; TTL-очистки нет, health-check тоже создаёт сессию.
- `rate`/`increase` учитывают сброс счётчиков; `increase` экстраполирует и может показывать дробные значения.
- Заказы до первого scrape не восстанавливаются в истории Prometheus. Счётчик заказов с labels появляется после первого заказа.
- При отсутствии заказов средний чек и отдельные p95 могут показывать No data. Это отличается от недоступного магазина; доступность оценивается по `up`.
- Перезапуск Node.js сохраняет JSON с заказами, но сбрасывает корзины, сессии и метрики процесса.

## Публикация с домашнего компьютера

```bash
docker compose -f compose.observability.yaml --profile public up -d
docker compose -f compose.observability.yaml logs tunnel-shop tunnel-grafana
```

В логах будут два HTTPS-адреса `*.trycloudflare.com`. Добавить адрес Grafana с завершающим / как `GRAFANA_PUBLIC_URL` в локальный `.env`, затем:

```bash
docker compose -f compose.observability.yaml up -d --no-deps grafana
```

VPN посетителям не нужен; проброс портов роутера не нужен. Публикуются только магазин и Grafana Viewer; Prometheus наружу не выставляется, тестовый reset отключён. Компьютер, Docker и интернет должны работать до завершения проверки. Quick Tunnel временный: остановка/пересоздание туннеля меняет URL. После этого нужно обновить ссылки в форме и `GRAFANA_PUBLIC_URL`. Для постоянного адреса нужен именованный туннель с доменом.

Остановить только этот стенд, сохранив данные:

```bash
docker compose -f compose.observability.yaml --profile public stop
```

Источники: [Playwright webServer](https://playwright.dev/docs/test-webserver), [Grafana provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/), [Cloudflare Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).
